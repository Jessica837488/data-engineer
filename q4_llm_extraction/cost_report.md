## 单条 vs 批量的成本对比（决策依据）

- **批量（16 条/次，最终方案）**：系统提示（约 400 tokens）被 16 条均摊，
  全量输入仅 1.07M tokens。
- **单条（对照估算）**：系统提示每条重复，仅此一项即 22,754 × ~400 ≈ 9.1M 输入
  tokens，是批量方案的 **8.5 倍**；且请求数 22,754 次 vs 1,030 次，在免费档限速
  下耗时将从 2.8h 膨胀到 20h+。
- 批量的代价：输出对齐复杂度（漏答/截断）。第一版按数组顺序对齐，长度不符即整批
  作废（试跑失败率 ~17%）；改为**输出带 id 字段按 id 对齐 + 缺失单条补漏**
  （188 次补漏），最终 fallback=0。
- **反直觉发现**：批量并非总是更省——单条补漏的 188 次请求中包含整批重试的
  余量；若模型漏答率高，"批量+补漏"的总 token 可能反超小批量。实测本数据集
  补漏仅占请求 18%，批量净收益成立。

## 成本结构分析（供模块 5 复用）

| 成分 | 占比 | 说明 |
|---|---|---|
| 输入 token | $0.29（影子） | 系统提示均摊后单条仅 ~47 tokens |
| 输出 token | $1.74（影子） | 占 86%——**输出 JSON 冗长是成本大头** |
| 规则层节省 | ≈40% 记录零成本 | 无文本 8,307 + 模板命中 257 + 兜底 821 |
| 消息级缓存节省 | ~6% | 相同消息只请求一次 |

**结论**：成本优化优先级 = 减少输出 token（压缩 JSON 字段/缩短 evidence_quote_en）
> 分流规则 > 消息缓存。这个结论直接支撑 Q5 的 LLM 成本估算。
