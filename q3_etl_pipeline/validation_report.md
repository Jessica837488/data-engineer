> 生成方式：`python q3_etl_pipeline/pipeline.py`（可复现，随机种子 42），
> 完整运行日志见 `pipeline_log.txt`。以下数字来自 2026-11-07 实际运行。

## 运行总览

| 项 | 值 |
|---|---|
| 总耗时 | **31.2 秒**（约束：100 万行 < 120 秒）|
| 实现 | 纯 pandas 向量化 + 分组池匹配；无 `iterrows()` 全表循环（仅退货匹配的小规模行级贪心，1.8 万行 × 小列表）|
| 断言 | 3 个输出共 15 条断言，全部通过（任一失败即中止管道）|

## 输出 1：`sales_facts.parquet`（BI 报表用）

| 指标 | 值 |
|---|---|
| 行数 | 1,005,779（占原始 1,067,371 行的 94.23%）|
| 金额合计 | 19,642,676.02 |
| 独立发票数 | 41,353 |
| customer_id 空值率 | 22.78%（有意保留：缺失 ID ≠ 非真实销售，是 Q1 发现的"线下散客"）|
| description 空值率 | 0.16% |
| unit_price = 0 行数 | 2,566（保留：0 价格是赠品/样品类真实业务行）|

**清洗漏斗**（每步行数均写入日志，可追溯）：

| 步骤 | 剔除行数 |
|---|---|
| 完全重复行（8 列全同） | 34,335 |
| 取消单（C 前缀） | 19,104 |
| 坏账调整（A 前缀） | 6 |
| 非产品 StockCode（POST/DOT/M/D 等） | 4,785 |
| Quantity <= 0（非 C 前缀的 0 价格对冲行） | 3,362 |

**类型规范**：`invoice_datetime` 为 datetime64、金额为 float64、ID 为 string、数量为 int64。

**口径决策与理由**：
1. **完全重复行剔除**：数据无行号列，无法区分"同一商品拆两行"与"重复录入"，
   取保守口径。34,335 行若不剔除，报表收入虚增约 3%——宁可少报不可虚报。
2. **保留 customer_id 缺失行**：这是销售事实表，不是客户表；Q1 已证明这批行
   是真实交易（UK 线下散客，98.8% UK、小额高频）。剔除它们会让 BI 报表少 13.7% 的钱。
3. **保留 0 价格行**：`total_amount = 0` 不影响收入统计，剔除反而丢失"赠送了多少货"的信息。

## 输出 2：`customer_features.parquet`（客户分群用）

| 指标 | 值 |
|---|---|
| 客户数 | 5,853（全部有 CustomerID 的客户）|
| recency_days | 中位数 94 天，均值 199.2 天 |
| frequency | 中位数 3 单，均值 6.25 单 |
| monetary | 中位数 856.01，均值 2,916.21 |
| is_one_time_buyer | 27.66% |

**口径决策与理由**：
1. **基准日 = 全表最大 InvoiceDate（2011-12-09 12:50）**，不是日历年末——
   数据在 12-09 截止，用 12-31 会让所有客户的 recency 平白多 22 天。
2. **frequency/monetary 用毛口径**（不含退货冲减）：退货在 `returns_log` 单独分析，
   且退货可能发生在购买很久之后，混入 RFM 会让"历史快照"随时间漂移。
   若业务要净口径，只需 join 退货金额二次加工——本文档明确标注这是决策而非遗漏。
3. **主要国家 = 计数最多的国家**（并列时取字典序），向量化实现，5,853 个客户 0.1 秒内完成。

## 输出 3：`returns_log.parquet`（退货分析用）

| 指标 | 值 |
|---|---|
| 行数 | 18,285（C 前缀且产品码；全部 Quantity < 0）|
| 退货金额 | -726,519.39（占真实销售 **3.70%**，量级合理）|
| 独立退货发票 | 7,405（平均每单 2.47 行）|
| 匹配成功 | 16,245（**88.8%**）|
| 其中：级联多单的部分匹配 | 144（原单量不足，匹配结果为多发票号 `;` 连接）|
| 无匹配（NULL） | 2,040（**11.2%**），其中 352 行 (1.93%) 因 CustomerID 缺失无法匹配 |

**匹配规则**（README 三个边界问题的明确答案）：

1. **多笔正向销售符合条件** → 取**离退货时间最近**的一笔（池按时间升序，倒序扫描）。
2. **买 10 个、分两次退 5+5** → 池中 `quantity_remaining` 逐次扣减，
   两次退货各自独立匹配（第二次匹配时第一次已消耗的量不再可用）。
3. **原单 quantity 比退货小** → 级联消耗更早的原单，匹配结果为多个发票号
   （如 `C489643` 退 2 件 → `525524;489654`）；池整体不足则记为部分匹配并计数。

**价格不参与匹配**：17,322 个"客户+商品"组内存在多个价格（促销/调价），
按价格过滤会造成大量漏配，因此只按 客户+商品+时间 匹配，价格差异留给下游分析。

**无匹配的三个真实原因**（日志含全部计数与示例）：
1. CustomerID 缺失（352 行）——退货时未登录，无从归属；
2. 原购买发生在数据集开始之前（2009-12-01 前）或从未在数据集中出现；
3. 同客户同商品的正销售全部晚于退货时间——**这曾是本管道的一个真实 bug**：
   修复前匹配率 91.6%，抽查发现 `C489449`（2009-12-01 退货）被匹配到 2010 年的
   `543376`；加入"原单必须早于退货时间"过滤并补上事后断言后，匹配率回落到
   真实的 88.8%。这个差值（498 行）就是"看起来更高实际是错"的代价。

## 断言清单（`validate_outputs`）

| 输出 | 断言 |
|---|---|
| sales_facts | quantity>0；unit_price>=0；total_amount>=0；无 C/A 前缀；StockCode 全部匹配产品码；日期列为 datetime；total_amount == quantity × unit_price |
| customer_features | recency_days>=0；frequency>=1；monetary>=0；first<=last；customer_id 唯一；is_one_time_buyer 与 frequency 严格一致 |
| returns_log | 全部 C 前缀；全部 Quantity<0；匹配引用的发票必须存在于销售明细；匹配原单时间必须早于退货时间（匹配引擎内）|
