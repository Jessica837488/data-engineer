# Online Retail II 数据真实结构发现（Q1.2）

> 所有数字均由实际数据计算得出，配套可复现代码见 `q1_code.py`（数据加载与口径定义）
> 及下方各节代码片段。计算环境：Python 3.12 / pandas 2.x，全量 1,067,371 行。
>
> **我的分析方法**：先不做任何假设地扫一遍前缀、极端值和缺失分布，让数据自己暴露结构，
> 再对每个"反直觉"现象回到原始行去追证据（同发票、同客户、时间差），
> 最后才下业务判断。顺序是 数据 → 证据 → 判断，而不是带着结论找数据。

## Q1：InvoiceNo 不只是数字

**代码**：
```python
df["InvoiceNo"].str[0].value_counts()
# 5    939382
# 4    108489
# C     19494
# A         6
c_inv = df[df["InvoiceNo"].str.startswith("C")]
c_inv["Quantity"].min(), c_inv["Quantity"].max()   # -80995, 1
```

**发现**：前缀共三种——`5`/`4` 开头是正常销售单（数字开头，共 1,047,871 行），`C` 开头 19,494 行，`A` 开头仅 6 行。

- **`C` = Cancellation（取消/退货单）**：证据有二：① 全部 19,494 行中 19,493 行 Quantity ≤ 0；② `C541433` 的 -74,215 件恰与一小时前客户 12346 在正常单 `541431` 买入的 +74,215 件对应，`C581484` 的 -80,995 件与 12 分钟前 `581483` 的 +80,995 件对应——**取消单是正常单的"负影"**。
- **`A` = Adjust bad debt（坏账调整）**：仅 6 行，全部 StockCode='B'、Description='Adjust bad debt'、CustomerID 缺失，其中 5 行 UnitPrice 为负、1 行为正（对冲）。

**销售总额统计中如何处理**：
1. `C` 前缀：计为负收入（净销售额口径），或从销售额中剔除后单独做退货分析——两种口径都可以，但要**在报表中固定一种并注明**。不能既算进去又当正常单分析。
2. `A` 前缀：从"商品销售"中剔除（它不是交易），只在公司级财务口径中保留。

## Q2：StockCode 不只是产品

**代码**：
```python
sc = df["StockCode"].str.strip()
non_prod = df[~sc.str.match(r"^\d{5,6}[A-Za-z]?$")]   # 非"5-6位数字(+字母后缀)"编码
len(non_prod) / len(df)                                # 0.70%
(df.loc[non_prod.index, "Quantity"] * df.loc[non_prod.index, "UnitPrice"]).sum()
# -38,792.13（净额，占总金额 -0.20%）
```

**发现**：7,465 行（0.70%）不符合产品编码规则，经逐一核对 Description，业务含义明确：

| StockCode | 行数 | 含义 | 净金额 |
|---|---|---|---|
| POST | 2,122 | 邮费 | +112,341.00 |
| DOT | 1,446 | 线上订单邮费（DOTCOM POSTAGE） | +322,647.47 |
| M | 1,421 | 手工调整（Manual） | -82,796.32 |
| C2 | 282 | 运费（CARRIAGE） | +13,386.00 |
| D | 177 | 折扣（Discount） | -13,484.54 |
| BANK CHARGES | 102 | 银行手续费 | -35,562.63 |
| S | 104 | 样品（SAMPLES） | -6,065.80 |
| AMAZONFEE | 43 | 亚马逊渠道佣金 | -260,763.58 |
| CRUK | 16 | 慈善机构佣金 | -7,933.43 |

另有一类"看起来异常其实正常"的编码：`85099B`、`79323P` 等——5-6 位数字**后缀字母**表示颜色/款式变体，是真实产品，不能误杀。

**占总行数 0.70%、占总金额 -0.20%（净额）**。绝对值不大，但 DOT 和 POST 两项合计 +43.5 万的正收入如果被当"产品销量"分析会严重扭曲商品排行；反之做 GMV 报表时它们该算收入却不该算商品销量——**同一批行，在不同下游用途里命运不同**。

## Q3：可疑极端值

**代码**：
```python
ext = df[df["Quantity"].abs() >= 10000]        # 15 行
df[df["UnitPrice"] < 0]                        # 5 行
```

**（a）Quantity = ±80,995 两条记录的完整信息**：

| InvoiceNo | StockCode | Description | Quantity | InvoiceDate | UnitPrice | CustomerID | Country |
|---|---|---|---|---|---|---|---|
| 581483 | 23166 | PAPER CRAFT , LITTLE BIRDIE | +80995 | 2011-12-09 09:15 | 2.08 | 16446 | United Kingdom |
| C581484 | 23166 | PAPER CRAFT , LITTLE BIRDIE | -80995 | 2011-12-09 09:27 | 2.08 | 16446 | United Kingdom |

**判断：真实业务，不是数据错误**。同一客户 12 分钟内买入又全额取消，两行金额精确抵消（±168,469.60）。可能的场景是批发客户误下单立即取消。同理 `541431`/`C541433`（±74,215 件，客户 12346）也是一对。真正可疑的反而是那批 Quantity≥10000 且 **UnitPrice=0.10/0.25/0** 的行——单价低到接近白送，更像渠道促销或数据录入异常，需按 Invoice 追溯。

**（b）UnitPrice 为负的记录**：5 行，共同特征：StockCode='B'、Description='Adjust bad debt'、InvoiceNo='A' 前缀、CustomerID 缺失、全部 UK。业务含义是**坏账核销**——客户破产/赖账后，会计把应收款冲销为负收入。

**（c）保留还是删除的判断标准**（我的三条标准）：
1. **看能否被业务解释**：能解释的（坏账、取消）保留但打标分流；不能解释且无法追溯的才考虑删。
2. **看金额量级 vs 分析目的**：±80,995 对"客户级 GMV"是毁灭性噪声（一个客户被放大 16.8 万），对"全网 GMV"则正负抵消无影响——按下游用途决定。
3. **看是否成对抵消**：成对出现且金额抵消的，净额口径下可保留。

## Q4：CustomerID 的"沉默大多数"

**代码**：
```python
miss = df[df["CustomerID"].isna()]       # 243,007 行
len(miss)/len(df)                        # 22.77%（行数口径）
miss.eval("Quantity*UnitPrice").sum() / df.eval("Quantity*UnitPrice").sum()
# 13.68%（金额口径）
```

**发现**：

| 口径 | 数值 |
|---|---|
| 缺失行数占比 | 22.77%（243,007 / 1,067,371） |
| 缺失金额占比 | 13.68% |
| 缺失组发票均额（客单价） | 301.53 |
| 有 ID 组发票均额 | 370.98 |
| 缺失组单行均额 | 10.86 |
| 有 ID 组单行均额 | 20.20 |

- **行数 vs 金额两个口径差异显著**：行数占 22.77% 但金额只占 13.68%，匿名订单是**高频小额**的。
- **国家分布差异**：缺失组 98.8% 来自 UK（240,029/243,007），且有香港（364）进入 TOP5；有 ID 组 UK 占 89.9%，德国（17,624）排第二。非 UK 客户几乎都有 ID，暗示**海外客户走注册下单流程，本地散客不注册**。
- **高频商品差异**：缺失组 TOP 是 `22355`(12,890 件)、`22086` 等小件日用品；有 ID 组 TOP 是 `84077`(107,489 件)、`85099B` 等大件批发品。
- **"匿名"人群推测**：结合 UK 集中 + 小额 + 日用品结构，最可能是**英国本地的线下/柜台散客、现金小额零售**，其次可能是未登录的官网游客订单。RFM 分群时把 24.3 万行匿名销售归并成一个伪客户"Anonymous"是常见做法，但**这会让 frequency/monetary 完全失真——匿名销售不应进入客户分群**，这正是 Q1.3 中 B 用途方案的核心决策。

## 方法论小结（我是怎么想的）

1. 先扫结构（前缀/极端值/缺失），让异常自己浮出来，再逐个回到原始行追证据；
2. 每个判断都要求"第二证据"：说 C 是取消单，就去找正常单里的正影；说是坏账，就看 Description 和 CustomerID 是否一致；
3. 判断"删不删"永远带着下游用途谈——同一行数据在报表、分群、推荐三种用途下的对错不同，这也是下一份 `cleaning_strategy.md` 的主线。
