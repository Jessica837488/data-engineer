## 2. 数据存储选型

订单主库保持 MySQL，订单是强一致的事务单元，状态机的每次翻转都发生在 OLTP，改动由 Debezium 捕获为 CDC 流。一切下游消费都以 Kafka 为唯一事实源，这样卖家后台看到的状态与交易库之间只隔一个消费延迟。

OLAP 选 ClickHouse。卖家要的 6 个月成交曲线是典型的宽表聚合查询，ClickHouse 的列存与向量化执行在亿级明细上仍能毫秒出数，物化视图按天预聚合后性能更稳。评价抽取结果、物流轨迹、订单状态快照都汇成宽表进 ClickHouse，Q3 产出的 Parquet 模型可以平移过来当表结构参考。

Kafka 承担三类流量：订单状态流（低延迟高可靠）、评价流（吞吐大、允许秒级攒批）、物流事件流（需要事件时间语义）。每个 topic 都配死信队列，解析失败的事件进 dlq 供人工回放。

Redis 只缓存卖家后台的会话与看板热数据，例如每个卖家最近 7 天的核心指标，TTL 60 秒。缓存的定位是挡住重复查询，成交明细永远回源到 ClickHouse。历史冷数据下沉到 S3 的 Parquet 数据湖，供离线回溯与模型训练。

## 3. LLM 部分如何避免成本失控

先算最坏情况的账。Olist 中约 41% 的评价带文本，100 万订单/天对应约 41 万条文本评价。若全部直接过 LLM：按 Q4 实测的单条消耗（输入约 47 tokens、输出约 70 tokens），每天约 4,500 万 tokens，年成本按 DeepSeek 单价折算约 7000 美元，其中输出占八成以上。这个数已经接近把一整个中台工程师的预算烧在写评价摘要上。

优化按四层展开，收益从大到小。第一层是 Q4 已验证的分流：规则词典与关键词模式能消化约四成流量，差评之外的高分评价用轻量情感模型打分，只有规则层无法覆盖的文本才进 LLM，这一步把日请求量压到约 8 万条。第二层是输出压缩，evidence_quote_en 与置信说明都做成可选字段，输出 token 减半直接砍掉近一半成本。第三层是消息级缓存，相同评价文本只请求一次，Olist 数据里完全重复的消息不少。第四层是批处理，沿用 Q4 的 16 条打包加 id 对齐方案，请求次数降一个数量级。四层叠加后年成本可以压到 1500 美元以内，同时设置两项硬保障：按小时的 token 预算熔断，以及置信度低于阈值的结果转人工抽检而不是无限重试。

## 4. 三个最大的风险点和应对方式

### 风险 1：消息积压拖垮 30 秒时效

**说明**：大促场景下订单状态变更量可能达到日常的十倍，Flink 反压后卖家后台看到的状态滞后从秒级滑向分钟级，承诺时效直接失效。

**应对**：Kafka 分区数按峰值三倍容量预留，消费者组支持水平扩容；监控消费 lag，超过阈值自动扩容并触发降级预案，降级时卖家后台改为直接查 OLTP 从库拿订单状态，实时链路只服务增量事件。

### 风险 2：LLM 成本与质量同时失控

**说明**：Q4 的评估给了真实警示，glm-4-flash 的类别准确率只有七成，sentiment 字段还系统性失效。质量隐患叠加免费档限速的不稳定，会让下游报表悄悄失真。

**应对**：线上采用模型分级，flash 档做粗分类，低置信子集升级到旗舰模型复判；每季度重跑 30 条分层人工标注评估，准确率跌破基线自动告警；成本熔断见第 3 节。

### 风险 3：事件乱序与重复消费污染 OLAP

**说明**：CDC 与 API 双通道写入，同一订单的状态可能乱序到达，Kafka 至少一次语义又会带来重复事件，宽表里出现倒退的状态和高估的 GMV。

**应对**：统一事件信封带事件时间与单调版本号，Flink 按事件时间加水印，迟到数据走侧输出；下游全部按事件幂等键 upsert，ClickHouse 用 ReplacingMergeTree 去重，GMV 类指标以订单终态为准做对账 job，每日与交易库核对误差。

## 5. 关于业务规模变化的考虑

10 万订单/天阶段，架构要克制。单机 MySQL 加 3 分区的 Kafka、一个 3 节点的 ClickHouse 集群就够，团队重点放在数据质量与监控上，避免为不存在的流量提前买单。

100 万订单/天阶段，变化体现在三处。MySQL 交易库按订单 hash 分库分表，CDC 改为按库粒度的多实例部署；Kafka 分区扩到 48 以上，Flink 作业引入 state backend 的 RocksDB 调优与 autoscaling；ClickHouse 走存算分离并按卖家分片，评价侧的 LLM 批处理改为独立 K8s 池错峰消费。真正的分水岭在于团队是否提前建好 lag 监控、成本看板与对账体系，这些能力在 10 万量级就该就位，扩容时只需加机器而不是改架构。
